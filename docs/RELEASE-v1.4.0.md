# v1.4.0 · 身份隔离修复与荣耀 / 应用宝渠道

> 修复刷新、回退或切换登录方式后，残留渠道账号被错误当成当前游戏身份的问题；同时恢复荣耀服扫码并新增应用宝 QQ / 微信扫码。官服或其他账号的游戏资料不会再写入原渠道账号记录，浏览器标签也不会继续显示错误的渠道名。

## 安装或升级

- 下载 [`sanguosha-channel-login.user.js`](https://github.com/softbad123/sanguosha-channel-login/releases/latest/download/sanguosha-channel-login.user.js)，在 Tampermonkey 中导入或覆盖安装。
- 建议使用 Tampermonkey `5.5.1` 或更新版本。安装后刷新三国杀登录页，页脚应显示 `v1.4.0 · 多渠道本地版 · 9 个渠道`。
- 不要同时启用旧的统一登录器、其他渠道登录器，或任何会向同一页面注入登录面板的脚本。
- 源码、使用说明和问题排查见 [`main` 分支 README](https://github.com/softbad123/sanguosha-channel-login#readme)。

## 新增与恢复渠道

### 荣耀

- 恢复荣耀服面板扫码：荣耀账号二维码 → 荣耀账号服务票据 → 荣耀游戏中心 → AnySDK → 游卡。
- 平台号 `50027`、游戏渠道号 `320463`；荣耀账号与游戏中心返回的身份必须一致。
- 二维码 Cookie、账号票据、游戏中心交换和本地会话恢复均有回归测试；实际扫码登录已验证。

### 应用宝

- 新增应用宝 QQ 扫码与微信扫码，平台号 `335`、腾讯 YSDK 渠道 `320460`、游卡网页渠道 `1036`。
- 应用宝 QQ 与微信使用独立的 `yybqq` / `yybwx` 会话和账号记录，不复用 WeGame 的 QQ / 微信流程。
- 微信登录按腾讯 YSDK 协议完成二维码签发、长轮询和一次性 code 校验；code 在校验请求发出前清除，失败后不能重放。
- 应用宝微信二维码签发与轮询使用独立的 `open.weixin.qq.com` / `long.open.weixin.qq.com` 受信主机策略。此前这两项请求未携带 `yybwx` 主机标记，被脚本自身的通用 API 白名单以 `ENDPOINT_DENIED` 拦截，因而二维码无法显示；本次修复仍保持严格的域名白名单，不放宽到任意主机。
- QQ 登录要求官方授权返回 `pay_token`，并通过 YSDK 校验。浏览器授权缺少该字段时会以 `YYB_QQ_PAY_TOKEN_MISSING` 安全失败，不生成账号记录。
- 腾讯 YSDK 的 `/auth/qq_verify_login` 响应中的 `openid` 使用独立 ID 空间，不保证等于 QQ OAuth 回调的 `openid`。脚本不再强制两者相等，账号身份、`access_token` 和 `pay_token` 固定保留 QQ 授权回调值，YSDK 响应仅用于校验结果及补充 `pf` / `pfKey` / 昵称；校验失败仍不会写入账号记录。
- AnySDK 兑换参数固定为应用宝平台，并校验返回的 `thirdparty` 为 `newysdk`、`cId` 为 `335`；其他平台票据会被拒绝。
- 腾讯 YSDK 的 `320460` 与游卡网页版的 `1036` 属于不同命名空间。此前脚本错误地要求游卡 grant 的 `channel_id` 必须等于 `320460`，导致扫码和手机授权成功后仍以 `YYB_CHANNEL_MISMATCH` 中断。现在 grant 兼容官方网页 `1036`、YSDK 别名 `320460` 或字段缺失，其他非空渠道号仍拒绝；进入游戏前统一规范化为 `1036`。
- 微信二维码签发与轮询已完成真实接口验证，QQ / 微信扫码与手机授权已验证；游卡 grant 后的渠道规范化仍需在本地测试版中分别复测。

## 问题与根因

复现路径如下：

1. 登录 Vivo 渠道服并保存账号记录，浏览器标签显示 `[Vivo服 · 角色名]`。
2. 刷新页面，或通过浏览器回退回到登录页。
3. 直接登录官服账号。
4. 浏览器标签仍显示 `[Vivo服 · 角色名]`，官服角色 ID 被写入原 Vivo 账号记录。

根因不是游戏身份探针读错，而是身份归属判断把两个不同可信级别的状态混在了一起：

- `sessionStorage` 中的 `ACCOUNT_CONTEXT` 只表示“这个标签页上次选择了哪个渠道账号”，刷新和回退后仍会保留。
- 旧逻辑在恢复该值后，把它与本次授权成功后的当前账号等同看待。
- 游戏资料到达时，`applyGameIdentity()` 优先使用“当前账号或预选账号”，没有先确认新身份是否属于该记录。
- 写入账号管理时没有检查已有角色 ID、登录账号或渠道账号是否与本次游戏身份冲突。
- 标签标题直接使用全局渠道配置，而不是已验证账号的实际归属。

因此，残留的 Vivo 预选状态会把官服角色资料吸收到 Vivo 记录中，同时让标题继续显示 `Vivo服`。

## 本版修复

### 选中状态与身份证明分离

- 新增仅存在于当前文档内存中的“已验证绑定”状态；刷新、回退和 `sessionStorage` 恢复都不能把它重建出来。
- `ACCOUNT_CONTEXT` 现在只用于恢复面板预选，不再参与游戏身份写入。
- 只有以下路径可以建立已验证绑定：
  - 本次渠道授权明确返回账号身份；
  - 一次性启动交接确认了账号记录；
  - 已保存登录状态恢复成功；
  - 游戏返回的角色 ID、登录账号或渠道账号与现有记录精确匹配。

### 冲突检测与拒绝覆盖

- 写入角色资料前，比较游戏身份与账号记录中的角色 ID、登录账号和渠道账号。
- 角色 ID 明确不一致时直接判为冲突，禁止覆盖。
- 已记录账号字段与本次身份明确不一致时同样判为冲突。
- 冲突时不会更新旧账号；脚本会解除本标签页的残留绑定、清除 `ACCOUNT_CONTEXT`，并写入 `game_identity_conflict` 诊断日志。
- 只有角色名、区服等不足以确认归属的部分资料不会触发写入，也不会被当成授权证据。

### 标签标题与游戏桥接

- 浏览器标签只显示已验证账号，并使用账号记录实际所属渠道，而不是固定使用全局渠道名。
- 刷新后仅恢复的预选账号仍可在面板中看到，但不会改变标签标题。
- 游戏页探针与游戏桥接返回的角色资料统一经过 `applyGameIdentity()` 身份门禁，避免后续新增入口绕过冲突保护。

## 回归测试

新增 `_test_identity_isolation.js`，覆盖：

- 刷新后残留 Vivo 预选，再登录官服：不得更新 Vivo 记录，标题必须恢复为普通三国杀标题。
- 刷新后登录同一 Vivo 账号：角色 ID 精确匹配时可以正常回填。
- 浏览器回退保留内存绑定时登录其他账号：仍必须识别冲突并拒绝覆盖。
- 全新授权账号尚无角色 ID：本次已验证绑定可以接收第一份游戏资料。
- 游戏只返回部分身份字段：不得仅凭预选状态写账号，也不得显示渠道标题。
- 静态检查身份解析不得读取 `sessionStorage` 或把 `window.name` 当身份证明；游戏桥接不得绕开统一身份门禁。

新增 `tests/_test_yyb_engine.js`，覆盖应用宝请求签名、微信专用受信主机策略、二维码解析与长轮询、一次性 code 消费、QQ `pay_token`、YSDK 与 OAuth `openid` 不同时的身份保持、校验失败不记账、AnySDK `newysdk` / `335` 绑定，以及 YSDK `320460` 与游卡网页 `1036` 的互不混用。该测试当前 15 项全部通过；同时验证了腾讯微信二维码接口返回有效图片和等待扫码状态。

现有账号直登、Vivo/OPPO/Steam 回调、游戏身份探针、面板折叠、更新日志与卸载清理测试全部继续通过；完整测试套件共 33 个测试文件通过。

## 已知限制

- 旧版本已经写入的错误账号资料不会自动删除或还原；升级后只会阻止新的错误写入。如记录已被污染，请在账号管理中手动纠正或删除后重新登录一次。
- 游戏身份只有在游戏实际下发角色资料后才可用于核对；资料未就绪时不会猜测归属。
- 本地恢复仍依赖渠道官方会话有效；渠道要求重新验证时，需要完成一次官方授权。
- 应用宝 QQ 链路依赖腾讯授权返回 `pay_token`；若官方浏览器授权不返回该字段，当前版本不会伪造或猜测票据。
- 应用宝 QQ / 微信的扫码与手机授权已确认；修复后的游卡 grant 和网页版游戏交接仍需分别复测，不能仅以“扫码成功”代替游戏侧识别与账号记录写入验证。
- 最终能否登录仍由渠道服务器、游卡服务器、账号状态和游戏服务器共同决定；本项目不绕过实名、支付、风控或官方授权。
